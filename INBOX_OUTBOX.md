# Simplifed version (v0)

To make franky-box radically simple, hyper-reliable, and bulletproof on SQLite, we can strip away everything that forces us to manage complex state, multi-step queries, or background cron workers.
Here is exactly what we can cut, how it simplifies the architecture, and the streamlined design that remains.
What We Can Drastically Simplify or Remove
Remove the State Machine entirely: Get rid of PENDING, PROCESSING, and COMPLETED states. A task is either in the table (needs to be done) or it isn't.
Merge Inbox and Outbox into ONE single Table: Instead of dual tables, synchronization transactions, and dual cleanups, use a single tasks table.
Inbox view: Rows where output IS NULL.
Outbox view: Rows where output IS NOT NULL.
Kill the Background Purge Cron: Instead of running a background worker to delete old data, let the API clean up after itself dynamically during standard GET or POST requests using standard SQLite date functions.
The Radically Simplified Architecture
1. The Single-Table SQLite Schema
We keep track of everything in one clean place.

PRAGMA journal_mode=WAL;

CREATE TABLE tasks (
    tenant_id TEXT NOT NULL,
    agent_id TEXT NOT NULL,
    task_id TEXT PRIMARY KEY,         -- auto-generated v4 UUID (generated in Zig, not by SQLite)
    action TEXT NOT NULL,
    payload TEXT NOT NULL,              -- JSON configuration input
    output TEXT DEFAULT NULL,           -- JSON result output (NULL means inbox item, NOT NULL means outbox item)
    try_count INTEGER DEFAULT 0,
    locked_until TEXT DEFAULT NULL,     -- ISO8601 string for visibility timeouts
    completed_at TEXT DEFAULT NULL,     -- ISO8601 string for rolling 7-day retention tracking
    workstream_id TEXT DEFAULT NULL     -- shared id grouping tasks in the same workstream (root task seeds it with its own task_id; follow-ups inherit it)
);

-- The only index needed to make claims and outbox streaming lightning-fast
CREATE INDEX idx_tasks_routing ON tasks (tenant_id, agent_id, output, locked_until);
-- Workstream lookup: WHERE workstream_id = ? returns the whole chain
CREATE INDEX idx_tasks_workstream ON tasks (workstream_id);


2. The Simplified Central Routing Pattern
When a human pushes a task, they don't look up agents. They just hit /api/v1/tasks/dispatch. franky-box looks at the table, finds which agent_id has the shortest queue for that action, and inserts it directly into that agent's queue.

INSERT INTO tasks (tenant_id, agent_id, task_id, action, payload, workstream_id)
VALUES (:tenant_id, :target_agent_id, :task_id, :action, :payload_json, :workstream_id);
-- :task_id is a v4 UUID generated by the server (SQLite has no built-in UUID function).
-- :workstream_id is NULL for a root task (the server then seeds it with :task_id) or
-- an existing workstream id to link a follow-up task to the same workstream.


3. Radical Simplification of Code & Queries
A. The Atomic Inbox Claim & Poison Pill Handler (Single Step)
We can claim work, increment the counter, handle visibility timeouts, and dump poison pills (tasks with try_count >= 3) all in one atomic step. We don't need separate states.

UPDATE tasks
SET 
    -- If it failed 3 times, we append an error output directly to instantly push it to the outbox as a failure
    output = CASE WHEN try_count >= 3 THEN '{"error": "Max retries exceeded. Poison pill aborted."}' ELSE NULL END,
    completed_at = CASE WHEN try_count >= 3 THEN strftime('%Y-%m-%dT%H:%M:%fZ', 'now') ELSE NULL END,
    try_count = try_count + 1,
    locked_until = strftime('%Y-%m-%dT%H:%M:%fZ', 'now', '+300 seconds')
WHERE task_id = (
    SELECT task_id FROM tasks
    WHERE tenant_id = :tenant_id 
      AND agent_id = :agent_id 
      AND output IS NULL -- It is still an uncompleted inbox item
      AND (locked_until IS NULL OR datetime(locked_until) <= datetime('now'))
    ORDER BY rowid ASC LIMIT 1
)
RETURNING task_id, payload, try_count;


B. Delivering Results to the Outbox (No Transactions Needed)
Because it is a single table, the agent doesn't need to coordinate moving data between an inbox and outbox using complex database transactions. It simply updates its own row. Updating output instantly turns the item from an Inbox entry into an Outbox entry.

UPDATE tasks
SET 
    output = :output_json,
    completed_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now'),
    locked_until = NULL
WHERE tenant_id = :tenant_id 
  AND agent_id = :agent_id 
  AND task_id = :task_id;


C. Reading the Outbox (The Consumer Agent Stream)
Downstream consumers or humans fetch results using the same table by querying rows that have completed outputs.

SELECT task_id, output, completed_at 
FROM tasks
WHERE tenant_id = :tenant_id 
  AND agent_id = :agent_id 
  AND output IS NOT NULL 
  AND datetime(completed_at) > datetime(:since_timestamp)
ORDER BY completed_at ASC;


D. Dynamic 7-Day Purge (No Background Cron Worker Required)
Instead of building a background worker daemon that could crash or leak memory, piggyback a deletion query whenever a human dispatches a new task or an agent requests a claim. This keeps your engine 100% self-cleaning without adding external architecture moving parts.

-- Executed passively in the background of standard API calls
DELETE FROM tasks 
WHERE completed_at IS NOT NULL 
  AND datetime(completed_at) <= datetime('now', '-7 days');


Why this is fundamentally more reliable:
Zero Distributed State Risk: There is no scenario where a task is marked done in the inbox but fails to write to the outbox. The write is a single row edit.
Fewer Lines of Code: Stripping out state changes makes testing simple.
Perfect for SQLite: SQLite thrives on single-table constraints, which eliminates row-locking contention issues entirely. [1]
